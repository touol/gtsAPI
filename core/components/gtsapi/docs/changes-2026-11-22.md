# gtsAPI 1.2.15 – 1.2.22: что нового (22.11.2026)

Для тех, кто пишет конфиги таблиц (`_build/configs/gtsapipackages.js`) и собирает пакеты PVExtra.
Все изменения обратно совместимы: старые конфиги работают как раньше. Исключения — раздел «Запись из формы»: там
закрыты две ошибки, на которые старые конфиги могли случайно опираться.

| Версия | Что |
|---|---|
| 1.2.15 | Свои резолверы пакета |
| 1.2.16 | 100 строк на страницу по умолчанию |
| 1.2.17 | Действия-ссылки (`actions.*.link`) |
| 1.2.18 | Фильтр по SQL-условию (`filter_sql`) |
| 1.2.19 | Права на поле (`groups` / `permissions` у поля) |
| 1.2.20 | Форма не пишет html / view и readonly-поля присоединённых классов |
| 1.2.21 | Пустая дата из формы не перезаписывает нулевую дату |
| 1.2.22 | html-колонки ищутся и сортируются (`filter_field`); SQL фильтра не уходит в браузер |

Примеры живут в tSklad (`_build/configs/gtsapipackages.js`: «Заказы 2», «Продажи 2») и Orgs2 / gsOrders.

---

## 1. Свои резолверы пакета (1.2.15)

Сборщик PVExtra-пакетов (`api/package`) после штатных резолверов подключает **php-файлы пакета** из
`core/components/<пакет>/resolvers/*.php` — по имени файла, файлы на `_` и `.` пропускаются. Внутри доступны
`$transport`, `$options`, `$object`, как в любом php-резолвере MODX.

Для того, что конфигами не описать: вычистить следы прежнего пакета, раздать политики группам сайта, поправить данные.

```php
// core/components/mypkg/resolvers/access_policies.php
if (!$transport->xpdo || !($transport instanceof xPDOTransport)) return false;
$modx =& $transport->xpdo;
$action = $options[xPDOTransport::PACKAGE_ACTION] ?? null;
if ($action !== xPDOTransport::ACTION_INSTALL && $action !== xPDOTransport::ACTION_UPGRADE) return true;
// ...
return true;
```

Резолвер едет внутри transport-пакета: gtsAPI 1.2.15+ нужен **на сайте, где пакет собирается**, а не на том, куда его
ставят.

Образцы:
- `tSklad/core/components/tsklad/resolvers/access_policies.php` — политики группам по `gtsapi_site_key` (только добавляет,
  ручные правки на сайте не перетирает; дописывает новые права в уже созданную политику — штатный резолвер разрешений
  её не обновляет);
- `tSklad/.../resolvers/weblinks.php` — id страницы в ярлык modWebLink (теги MODX в `content` при установке вырезаются);
- `gsOrders/.../resolvers/cleanup_gsorder.php` — убрать прежний пакет при переименовании (без деинсталляции).

## 2. 100 строк на страницу по умолчанию (1.2.16)

`options` отдаёт `limit: 100`, если в конфиге таблицы `limit` не задан (раньше `false`, и PVTables брал 10).
TanTable и TanMobileList стартуют со 100. Писать `limit: 100` в каждом конфиге больше не нужно; `limit` — только если
нужно другое число, `limit: 0` — без страниц, как раньше.

## 3. Действия-ссылки (1.2.17)

Кнопка строки, пункт меню строки (`menu: 1`) или кнопка шапки, которая открывает адрес:

```js
actions: {
    order2:    { row: true, menu: 1, label: 'Заказ 2', icon: 'pi pi-list',
                 link: { setting: 'tsklad_p_order2', params: { id: 'id' } } },
    transport: { row: true, menu: 1, label: 'Транспорт', icon: 'pi pi-truck', permissions: 'tsklad_orders_edit',
                 link: { id: 425, params: { order_id: 'id', type_order_id: '=1' } } },
}
```

`link` — одно из:

| Ключ | Что |
|---|---|
| `id` | id ресурса → `makeUrl` |
| `setting` | системная настройка с id ресурса (то, что пишет `resources.js` в `config_name`) |
| `uri` | путь от корня сайта |
| `url` | адрес как есть (только `http(s)://` и относительные) |
| `tpl` | шаблон Fenom по строке |

`params` — GET-параметры: имя ⇒ поле строки; значение с `=` в начале — константа. `target` — по умолчанию `_blank`.

Адрес строки считает `read` и кладёт в `rows[i].gtsapi_links[имя действия]`, у кнопки шапки — `options` в `href`.
Клиенту уходит готовый адрес, шаблон и настройки — нет. Права действия (`groups` / `permissions`) работают как у любого
действия: без прав пункта нет.

## 4. Фильтр по SQL-условию — `filter_sql` (1.2.18)

Для колонок, которых нет в таблице как есть: склейки `GROUP_CONCAT`, подзапросы, выражения. Обычный фильтр по
присоединённым строкам ломает склейку (в «ТН № 101/102» после фильтра осталась бы только найденная).

```js
tns: { label: 'ТН №', type: 'text', readonly: 1,
       filter_sql: "EXISTS (SELECT 1 FROM modx_doc1c_payment_link fl JOIN modx_doc1c_tn fd ON fd.id = fl.doc1c_id"
                 + " WHERE fl.order_id = tSkladOrders.id AND fl.type_doc1c = 2 AND fd.nomer_1c {match})" },
price2: { ..., filter_sql: 'BaseOtchet.price {match}' },
```

`{match}` gtsAPI подставляет по режиму фильтра: `= 'X'`, `LIKE '%X%'`, `LIKE 'X%'`, `< 'X'`, даты, `IN (...)`,
`IS NULL`… Значение — через `quote()`, для LIKE экранируются `%`, `_`, `\`.

**Безопасность.** SQL берётся только из конфига (`fields.*` или `filters.*`) — от клиента gtsAPI принимает лишь значение
и режим. Режим — из белого списка, неизвестный — условия нет. Значение — только скаляр (у `in` — список скаляров).
Проверено тестом инъекций: `tSklad/tests/e2e/orders2_api.mjs`.

## 5. Права на поле (1.2.19)

```js
price2: { label: 'Цена всего', type: 'decimal', ..., permissions: 'tsklad_orders_prices',
          hide_keys: ['price', 'sum_tn_cost'] },
```

`groups` (группы через запятую) и / или `permissions` (разрешения MODX через запятую) — кто видит поле. Как у таблиц:
заданы оба — нужны оба. Без прав поле:
- убирается из `options`, Excel и печати;
- не пишется (из запроса удаляется), по нему не фильтруют и не сортируют — цену не подобрать фильтром «цена = X»;
- вырезается из ответа (`rows`, `object`) вместе с колонками из `hide_keys` — сырыми колонками, из которых поле собрано
  (иначе значение осталось бы в JSON и было видно в инструментах разработчика браузера).

Один вид таблицы для разных групп: «Заказы 2» видят производство и склад, деньги — только менеджеры
(`tSklad/tests/e2e/price_access.mjs`).

Цвет строки (`row_setting`) считается на сервере до вырезания: если он зависит от скрытого поля, пользователь без прав
видит подсветку, но не значение.

## 6. Запись из формы (1.2.20, 1.2.21)

Форма PVTables при сохранении шлёт строку целиком. Закрыто три ошибки:

1. **html / view — только отображение.** У `html` с `tpl` значение поля при чтении заменено разметкой; форма отправляла
   её обратно, и сервер отвечал «Поле … доступно только для чтения». Теперь такие поля из запроса записи отбрасываются.
2. **readonly-поля присоединённых классов не пишутся.** Раньше проверку «только для чтения» они пропускали (есть
   комментарий «JOIN-поля — пропускаем»), а `class_link` записывал их значениями из формы: правка примечания
   перезаписывала «План», даты и т. п., а пользователь с правом правки мог подменить их запросом. Условное
   `readonly: { groups, permitions }` учитывается.
3. **Пустая дата не затирает нулевую.** Нулевая дата (`0000-00-00`) показывается пустой, форма возвращает `null` —
   раньше в базу писался `NULL`. Теперь пустое значение `date` / `datetime` при нулевой дате в базе (своей таблицы и
   присоединённой по `class_link`) не пишется. xPDO отдаёт нулевую дату и как `-0001-11-30` — учтено.

Если конфиг рассчитывал писать через форму readonly-поле присоединённого класса — это больше не работает: снимите
`readonly`.

## 7. html-колонки ищутся и сортируются (1.2.22)

```js
excel_id: { label: 'Заказ №', type: 'html', readonly: 1, filter_field: 'excel_id',
            tpl: `<a href="{'tsklad_p_order2' | option | url}?id={$id}">{$excel_id}</a>` },
poroshok: { label: 'Порошок', type: 'html', readonly: 1, filter_sql: 'BaseOtchet.poroshok {match}', tpl: '...' },
```

- `filter_field` — колонка из `select`, по которой фильтруется и сортируется html-поле (показывается разметка). Можно
  `Класс.колонка` — тогда только фильтр.
- С `filter_sql` html-колонка получает фильтр (без сортировки).
- PVTables включает фильтр / сортировку у html-колонки только при этих опциях; без них — как раньше.

`options` больше не отдаёт текст `filter_sql` клиенту — только `filter_sql: true`.
